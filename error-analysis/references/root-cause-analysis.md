## 5 Whys（なぜなぜ分析）

「なぜ？」を繰り返して深掘りする最もシンプルな手法。

### 手順

1. 問題を定義する。
2. 「なぜそれが起きたのか？」と問い、直接の原因を挙げる。
3. その原因に対して、さらに「なぜ？」と問う。
4. これを5回（または真因が見つかるまで）繰り返す。

### ポイント

- **他責にしない**: 「Aさんがミスしたから」ではなく「ミスを誘発する仕組みだったから」と考える。
- **事実に基づく**: 推測ではなく、確認された事実でつなぐ。
- **解決可能か**: 自分たちで解決・対策できる原因に着地させる。

### 例：デプロイに失敗した

1. **なぜ？**: ビルドエラーが発生した。
2. **なぜ？**: 依存ライブラリのバージョン不整合が起きた。
3. **なぜ？**: `package-lock.json` がコミットされていなかった。
4. **なぜ？**: `.gitignore` の設定ミス。
5. **なぜ？**: **プロジェクト初期セットアップ時にテンプレートをそのまま使い、内容を確認していなかった。**（根本原因）

**対策**: テンプレートの見直しと、CIでのロックファイル存在チェックの追加。

## 特性要因図 (Fishbone Diagram)

「魚の骨」のような図を使い、要因を構造的に整理する。

### 構成要素（4M）

システムトラブルでは、以下の観点で要因を洗い出すことが多い。

- **Machine** (設備・システム): サーバー、ネットワーク、ツール
- **Material** (材料・データ): 入力データ、設定ファイル
- **Method** (方法・プロセス): 手順書、ワークフロー、アルゴリズム
- **Man** (人): スキル、疲労、コミュニケーション

### 手順

1. 頭の部分に「問題（結果）」を書く。
2. 背骨を引き、大骨（4Mなど）を書く。
3. 各大骨に対して、考えられる要因（小骨）を書き出す。
4. 真因と思われるものに印をつける。

## アイスバーグモデル

問題を3つの層で捉える。

1. **出来事 (Events)**: 何が起きたか？（エラー、障害）
   - *対応*: リアクティブな対処（再起動、バグ修正）
2. **パターン (Patterns)**: 傾向は？（毎週起きる、特定のユーザーで起きる）
   - *対応*: 予測と予防（監視強化、リソース増強）
3. **構造 (Structures)**: 何がパターンを生んでいるか？（アーキテクチャ、組織文化）
   - *対応*: 抜本的な改革（設計変更、プロセス改善）

RCAでは「構造」レベルまで掘り下げることを目指す。

## 再発防止策

原因を特定したら、再び起きないようにする。

### 対策の階層

効果が高い順：

1. **除去 (Eliminate)**: 原因そのものをなくす。（機能削除、自動化）
2. **予防 (Prevent)**: 起きないようなガードを入れる。（型システム、Lint、テスト）
3. **検知 (Detect)**: 起きたらすぐにわかるようにする。（モニタリング、アラート）
4. **緩和 (Mitigate)**: 起きても影響を小さくする。（リトライ、サーキットブレーカー）
5. **手順 (Procedural)**: 注意喚起、マニュアル化。（効果は低いがコストも低い）

### 「恒久対策」とは

「気をつける」「ダブルチェックする」は恒久対策ではない。**人間がミスできない仕組み**を作ることが真の恒久対策。
