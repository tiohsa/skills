# test-driven-development

## 概要
`test-driven-development` は、テストを先に書き、実装を後から進めるTDDのための Skill です。Red-Green-Refactor サイクル、AAAパターン、テスト命名、モック・スタブ、FIRST原則を使って、必要最小限の実装と継続的な改善を支援します。

## 使う場面
- 新しい振る舞いをテストから設計したい。
- バグを再現する失敗テストを書いてから修正したい。
- ユニットテスト、モック、スタブの構成を決めたい。
- テスト名やテストケースの粒度を整理したい。

## 使わない場面
- すぐに動作確認できない探索的なプロトタイプだけが目的の場合。
- E2Eだけで十分で、ユニットレベルの設計フィードバックが不要な場合。
- テストを後付けの確認作業としてしか使わない場合。

## 実行フロー
1. 実装したい振る舞いを小さな期待結果に分解する。
2. Red フェーズで失敗するテストを最小限書く。
3. Green フェーズでテストを通す最小限のコードを書く。
4. Refactor フェーズでコードを改善し、テストが通ったままにする。
5. AAAパターン、明確なテスト名、FIRST原則に照らしてテストを見直す。

## 生成・更新する主な成果物
- 失敗から始めるユニットテスト
- モックやスタブを使った依存分離テスト
- テストを通す最小限の実装コード
- リファクタリング後も通る回帰テスト

## 注意点
- 失敗するテストなしに本番コードを書き始めない。
- テストも実装も、今必要な最小単位に留める。
- モックを使いすぎて実際の振る舞いから離れない。
- テスト同士が順序や共有状態に依存しないようにする。
