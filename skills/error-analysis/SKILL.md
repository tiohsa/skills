# エラー解析

エラーの原因を体系的に特定し、解決するためのガイド。

## 解析の基本ステップ

1. **現象の確認**: 何が起きたか？（エラーメッセージ、挙動）
2. **再現確認**: どのような手順で起きるか？（再現性）
3. **範囲の特定**: どこで起きているか？（フロント、バック、DB）
4. **原因の特定**: なぜ起きたか？（コード、設定、データ）
5. **修正と検証**: どう直すか？（修正、テスト）
6. **再発防止**: どう防ぐか？（テスト追加、設計変更）

---

## エラーメッセージの解読

エラーメッセージは情報の宝庫。読み飛ばさずに分析する。

### 読むべきポイント

1. **エラータイプ**: 何の種類のエラーか？ (`SyntaxError`, `NullPointerException` など)
2. **メッセージ**: 具体的な内容は？ (`Unexpected token`, `undefined is not a function`)
3. **スタックトレース**: どこで起きたか？（ファイル名、行番号）

### 解析テンプレート

```markdown
- **エラー**: [エラーメッセージ全体]
- **場所**: [ファイル名]:[行番号]
- **直前の操作**: [トリガーとなったアクション]
- **予想される原因**: [仮説]
```

詳細は [debugging-techniques.md](references/debugging-techniques.md) を参照。

## 根本原因の特定 (RCA)

表面的な修正（絆創膏対応）ではなく、根本原因を叩く。

### 5 Whys（なぜなぜ分析）

「なぜ？」を5回繰り返して真因に到達する。

**例: サーバーがダウンした**

1. **なぜ？**: メモリ不足エラーが発生したから。
2. **なぜ？**: 特定の処理で大量のメモリを消費したから。
3. **なぜ？**: ループ内で巨大な配列を生成していたから。
4. **なぜ？**: ページネーションなしで全件取得していたから。
5. **なぜ？**: **データ量が増加することを想定していない設計だったから。**（根本原因）

**対策**: ページネーションを導入し、取得件数を制限する。

詳細は [root-cause-analysis.md](references/root-cause-analysis.md) を参照。

## エラーの種類と対応

詳細は [error-types.md](references/error-types.md) を参照。

| 種類 | 特徴 | 主な原因 |
|------|------|----------|
| **構文エラー** | 実行前に検出 | タイポ、閉じ忘れ |
| **実行時エラー** | 実行中に停止 | Null参照、型不一致、リソース不足 |
| **論理エラー** | 止まらないが結果が不正 | アルゴリズム間違い、条件式の誤り |

## トラブルシューティングの心構え

- **事実と推測を分ける**: 「こうなっているはず」と思い込まない。
- **一度に一つだけ変える**: 複数の変更を同時に行うと原因がわからなくなる。
- **ログを見る**: 推測する前に証拠を集める。
- **最小構成で再現**: 余計な要素を排除して問題を切り分ける。
