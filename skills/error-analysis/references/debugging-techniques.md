## スタックトレースの分析

エラー発生時の呼び出し履歴を読み解く。

### 読み方の手順

1. **一番上（または一番下）を見る**: 言語によってエラーの発生元が表示される位置が異なる（Pythonは下、JSは上など）。
2. **自分のコードを探す**: ライブラリやフレームワークのコードは無視し、自分が書いたファイルの行を探す。
3. **エラーメッセージを読む**: 何が起きたかを理解する。

### 例（Python）

```
Traceback (most recent call last):
  File "main.py", line 15, in <module>
    process_data(user_input)
  File "main.py", line 8, in process_data    <-- 自分のコード
    return calculate_ratio(items)
  File "utils.py", line 42, in calculate_ratio <-- 自分のコード
    return total / count
ZeroDivisionError: division by zero           <-- エラー原因
```

**分析**: `utils.py` の 42行目で `count` が 0 になっているため、ゼロ除算が発生した。

## ログ分析

推測ではなく事実に基づいたデバッグを行う。

### ログレベルの活用

- **ERROR**: 即時対応が必要なエラー
- **WARN**: 問題の可能性があるが継続可能
- **INFO**: 正常な動作の記録（開始、終了など）
- **DEBUG**: 開発時の詳細情報（変数の値など）

### printデバッグ vs ロガー

一時的な確認には `print` も有効だが、持続的な解析にはロガーを使用する。

```python
# ❌ print
print(f"User: {user}")

# ✅ logger
logger.info("User login attempt", extra={"user_id": user.id})
```

### ログに含めるべき情報

- タイムスタンプ
- トランザクションID（リクエストID）
- ユーザーID
- コンテキスト情報（変数の値、状態）

## 二分探索デバッグ

問題の範囲を効率的に絞り込む。

### 手順

1. **範囲を定義**: 正常に動いていた地点（A）と、エラーが起きる地点（B）を特定。
2. **中間点をチェック**: AとBの中間（M）で状態を確認。
   - Mでエラー → 問題はA〜Mの間
   - Mで正常 → 問題はM〜Bの間
3. **繰り返し**: 範囲を半分ずつ狭めていく。

### git bisect

Gitの履歴からバグが混入したコミットを特定する。

```bash
git bisect start
git bisect bad            # 現在のコミットはバグあり
git bisect good <commit>  # 過去の正常なコミット
# 自動的にチェックアウトされるので、動作確認して
git bisect good  # または git bisect bad
# を繰り返す
```

## ラバーダック・デバッグ

問題を誰か（あるいはアヒルのおもちゃ）に説明することで解決策を見つける。

### 手順

1. エラーの内容と、コードが何をしているかを一行ずつ説明する。
2. 説明している途中で、自分の思い込みや論理の飛躍に気づくことが多い。
3. 「あ！わかった！」となる。

**効果**: 脳のモードが「書く」から「説明する」に切り替わり、客観的な視点が得られる。
