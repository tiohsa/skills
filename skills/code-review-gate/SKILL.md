# code-review-gate

Perform disciplined, evidence-based code reviews that converge on a clear merge decision rather than trapping implementation and review agents in an infinite fix-and-rereview loop.

## Purpose

Provide a deterministic, bounded review protocol for AI-generated and human-written diffs so reviewers verify acceptance criteria, separate CI-enforceable checks from semantic defects, and reach a clear `MERGE`, `FIX_REQUIRED`, or `ESCALATE` decision within at most two rounds.

## Prerequisites

- Access to the target diff (`git diff <base>..HEAD` or `<R1_commit>..HEAD`) and relevant source files.
- Acceptance criteria (`SPEC.md`, issue description, or task prompt) and automated check results (tests, linters, type checks, SAST) when available.

## When to Use

- Reviewing code changes, pull requests, or `git diff` outputs generated by AI coding agents or human developers.
- Performing a follow-up re-review after fixes have been applied (`git diff <R1_commit>..HEAD`).
- Evaluating whether a change satisfies `SPEC.md` acceptance criteria and passes quality gates for merge.
- Setting up review checklists, severity triage rules, or repository review guidelines (`AGENTS.md`, `CLAUDE.md`, `BUGBOT.md`).

## Core Principles

- **Define Done by Risk Threshold, Not Zero Comments:** Code review improves overall codebase health; it is not an exhaustive search for every theoretical flaw. If no blocking defects remain and required checks pass, approve for merge.
- **Suppress Bug-Hunting Bias:** Never invent hypothetical bugs or unstated requirements just to produce feedback. If the diff meets acceptance criteria with no blocking defects, explicitly report zero blocking issues.
- **Require Verifiable Evidence:** Every blocking finding must cite concrete file lines, reproduction inputs, or a failing test case. Speculative logic claims without evidence cause false rejections and destructive rewrites.
- **Forbid Full Fix Code Generation:** Do not write replacement code patches in review findings; specify only the behavioral requirement and exact fix boundary (`Scope`) to prevent false-rejection rationalization.
- **Defer Deterministic Checks to CI:** Do not spend review cycles on formatting, naming style, lint rules, or basic type errors handled by linters, formatters, type checkers, or SAST tools.
- **Constrain Blast Radius:** Restrict reviews and requested fixes strictly to the current diff (`base..head`). Route unrelated refactoring ideas or surrounding improvements to follow-up issues or `TODO.md` so fixers do not overreach and introduce regressions.
- **Separate Reviewer Context:** Execute reviews in a fresh session/context separate from the implementation session whenever possible, as self-critique within the same context degrades reliability.

## Step-by-Step Review Workflow

### Step 1: Lock Scope and Acceptance Criteria

Before inspecting implementation details, establish the review boundaries:

1. Identify the target diff (Round 1: `git diff <base>..HEAD`; Round 2 re-review: `git diff <R1_commit>..HEAD`).
2. Extract the stated **Goal**, **Non-goals / Out-of-scope**, **Acceptance Criteria (AC)**, and **Constraints (Security / Performance)** from `SPEC.md` or the task prompt. If specifications are missing or ambiguous, state your assumption explicitly rather than fabricating hidden requirements.
3. Flag any changes touching items listed under `Non-goals / Out-of-scope` as scope violations, and recommend splitting oversized diffs that mix unrelated concerns before deep review.

### Step 2: Separate Deterministic Checks from Semantic Review

Verify whether automated checks (unit/integration/E2E/regression tests, type checks, linters, SAST, dependency/secret scans) have run and passed:

- If required automated checks failed, halt deep review and instruct the author to fix only the failing gates first.
- Exclude style, indentation, and formatting preferences from your findings unless they violate an explicit repository rule.

### Step 3: Conduct Evidence-Based Diff Review (Round 1)

Audit the diff against the locked `Acceptance Criteria`, `Constraints`, compatibility contracts, and security boundaries. Classify every observation into one of four severity tiers:

- **Blocker (Merge Prohibited):** Critical failure, security vulnerability (auth bypass, SQLi, XSS, secret exposure), or irreversible data corruption/loss.
- **Major (Merge Prohibited by Default):** Violation of explicit Acceptance Criteria or Constraints, out-of-scope modification violating Non-goals, deterministic logic bug, race condition, or breaking API/DB contract change.
- **Minor (Merge Allowed with Follow-Up):** Localized maintainability issue, duplicate logic, or minor edge-case fallback that does not violate AC. Record as a follow-up issue or `TODO.md` entry rather than blocking merge.
- **Nit (Non-Blocking):** Naming preference, comment phrasing, or minor stylistic suggestion. Omit by default, or mark explicitly as `[Nit / Non-blocking]`.

For every **Blocker** or **Major** finding, provide concrete evidence (including a failing input or test scenario for logic bugs), risk impact, and the minimal required fix boundary using the Blocking Finding Template below.

### Step 4: Scope Minimal Fixes and Execute Bounded Re-Review (Round 2 Max)

When fixes are submitted after Round 1:

1. Inspect only the incremental diff (`git diff <R1_commit>..HEAD`) plus directly affected call paths and regression tests. Do not re-audit the entire codebase from scratch.
2. Verify that each prior Blocker/Major finding is resolved without introducing new regressions or fixer overreach.
3. **Circuit Breaker Rule (Max 2 Rounds):** Limit the review-fix cycle to a maximum of **2 rounds**. If Major issues still remain after Round 2, stop iterating and escalate to the human decision owner as a specification gap, architectural flaw, or oversized PR requiring decomposition.

### Step 5: Issue the Quality Gate Verdict

Conclude every review with the structured Review Completion Gate summary based on the completion formula:

`Done = AcceptanceCriteriaPass AND RequiredChecksPass AND Open(Blocker) = 0 AND Open(Major) = 0 AND ResidualRisk <= AgreedThreshold`

- **Security Unverified Rule:** If the diff modifies authentication, authorization, billing, external input handling, or database migrations and automated security/test checks are `UNVERIFIED`, output `ESCALATE` even when `Open Blocker` is `0`.
- Output `MERGE` when all conditions hold.
- Output `FIX_REQUIRED` when Round 1 finds Blocker/Major items.
- Output `ESCALATE` when Blocker/Major items persist after Round 2 or critical/unverified security or data risks require human sign-off.

## Output Templates and Language Rules

- **Language Rule:** Keep all gate labels (`MERGE`, `FIX_REQUIRED`, `ESCALATE`, `PASS`, `FAIL`, `UNVERIFIED`, `Blocker`, `Major`, `Minor`, `Nit`) in English, and write all descriptions and explanations in the user's language.

### Blocking Finding Template (Blocker / Major)

```markdown
[Blocker | Major] <Short descriptive title>
- Evidence: <File path, line numbers, concrete failing input, or test case>
- Risk: <What breaks or which Acceptance Criterion / Constraint is violated>
- Required action: <Minimal behavioral fix needed (do not write full replacement code)>
- Scope: <Exact boundary defining when this item is resolved>
```

### Review Completion Gate Template

```markdown
### Review Completion Gate
- Acceptance Criteria: PASS / FAIL
- Required Checks (Tests / CI): PASS / FAIL / UNVERIFIED
- Open Blocker: <count>
- Open Major: <count>
- Deferred Minor (Follow-up Issue / TODO.md): <count or list>
- Residual Risk: LOW / MEDIUM / HIGH
- Decision: MERGE / FIX_REQUIRED / ESCALATE
```

## Gotchas

- **Avoid Oscillating Preferences:** Never ask an author to rewrite working imperative loops into functional chains (or vice versa) across rounds.
- **Watch for Test Overfitting:** Check whether new tests genuinely validate Acceptance Criteria rather than hard-coding expected outputs or mocking away the actual logic under test.
- **Do Not Gate Security Solely on LLM Review:** AI reviewers can miss subtle injection, deserialization, or authorization flaws. Always require deterministic SAST, dependency scans, and targeted abuse-case tests for security-sensitive paths.

## Limitations

- **Not a Replacement for Automated Checks:** Semantic review cannot reliably catch formatting, type errors, or deep security vulnerabilities on its own; deterministic CI/SAST gates remain required.
- **Diff-Scoped Only:** Findings are bounded to `base..HEAD`; pre-existing technical debt outside the diff is routed to follow-up issues rather than blocked here.

## Troubleshooting

| Symptom | Cause | Solution |
| --- | --- | --- |
| Review stalls in repeated fix-and-rereview loops | Unbounded scope or speculative findings | Enforce the 2-round circuit breaker and require concrete evidence for every Blocker/Major |
| Acceptance criteria are missing or vague | No `SPEC.md` or incomplete prompt | State assumptions explicitly in Step 1 and escalate if critical requirements are ambiguous |
| Security-sensitive diff has no test/SAST results | Automated checks were skipped or unavailable | Mark `Required Checks` as `UNVERIFIED` and output `ESCALATE` |
